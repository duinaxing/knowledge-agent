# 系统 100 人并发压力测试技术方案与运行手册

## 目标和隔离

验证 100 人日常在线使用与 100 人在 1 秒内集中提问。使用当前电脑隔离实例：API 8100、Embedding 8101、模型网关 8102、PostgreSQL 数据库 `knowledge_loadtest_100`、文件 `runtime/loadtest/files`。业务 `.env`、数据库和服务不修改。端口冲突直接退出，不终止占用者。

测试与业务使用同一 PostgreSQL 集群，客户端与所有服务共享本机资源，因此结论仅针对本机与本次数据规模。执行前关闭无关高负载程序，但无需删除业务资料。

默认保留问答执行槽位 4、总期限 60 秒、模型调用超时 20 秒、工具超时 5 秒以及现有登录/问答限流。先测容量，不通过延长超时掩盖排队。

## 安装与一键运行

在 `project` 目录运行；先使用 `start-postgres.ps1` 确保本机数据库已启动。Python 路径沿用当前项目环境，BGE 权重沿用本地只读模型文件。

```powershell
& 'D:\Anaconda\envs\hello_agents_py311\python.exe' -m pip install -e './backend[loadtest]'

# 完整模拟测试（默认），约 75–90 分钟，首次另需数据准备时间
./run-loadtest.ps1

# 冒烟：功能/隔离校验、100 人短时读取、一轮 100 人峰值
./run-loadtest.ps1 -Profile smoke

# 优化链路 + 8 槽位；禁用快路径可复测原 Agent
./run-loadtest.ps1 -Profile smoke -Workers 8
./run-loadtest.ps1 -Profile smoke -Workers 4 -LegacyAgent

# 仅用 4 个用户快速验证延迟、429、超时、worker 重启恢复
./run-loadtest.ps1 -Profile faults

# 真实 DeepSeek：10 个预热、90 个混合问答、100 个集中问答
./run-loadtest.ps1 -Real

# 只清理独立压测数据库和上传文件，保留结果报告
./run-loadtest.ps1 -Cleanup
```

真实模式始终执行真实阶段规定的 200 问答流程，`-Profile` 仅控制模拟模式。真实模式读取现有密钥，不输出密钥；模型请求上限 1000，重试计数。每次执行独立预算，新执行会重新获得预算，不是账号总消费限制。

所有模式均持有独占启动锁。脚本正常退出或异常时关闭本轮创建的服务，不关闭业务进程。强制结束父进程可能留下子服务；下次启动检测端口占用后拒绝运行，进程记录位于结果目录，不会自动杀死身份不明的进程。

## 工具结构和数据流

代码位于 `backend/src/knowledge_loadtest/`，不由业务应用导入：

| 模块 | 用途 |
|---|---|
| launch | 环境变量隔离、启动锁、端口检查、服务启动/回收 |
| prepare | 数据库迁移、合成数据、真实上传解析索引发布、限定清理 |
| gateway | 兼容 `/chat/completions`、可控模拟延迟、真实转发硬预算 |
| runner | 100 个独立 HTTP 用户、CSRF、SSE、场景、结果核对 |
| worker | 仅在测试进程包装领取函数，记录真实领取时刻 |
| monitor / report | 资源与数据库采样、原始记录、CSV、报告与图 |

每个用户独立 Cookie、CSRF、会话和请求标识。流程：登录 → 新会话 → 提交问题 → SSE → 最终答案 → 引用 → 历史核对。功能阶段重复提交相同幂等键，要求返回同一任务。隔离检查覆盖 100 个用户读取他人会话与私人文档。

固定种子 `20260915`：100 员工、10 组、300 文档（MD/TXT/PDF 各 100）、30 个旧版本；组织公开、组授权和个人授权各 100。每人 10 个会话、每会话 20 轮合成历史。标准题库记录文档版本、校验码、目标片段和授权用户。英文文本型 PDF 用于避免字体依赖，仍通过真实 PDF 解析器与中文 BGE 模型索引。

首次完成准备后复用数据；若需完全相同的起始数据，先运行限定清理，再重新压测。中途准备失败会拒绝复用不完整数据，须清理后重新准备。历史预置通过 ORM 批量写入，文档使用业务上传、后台索引和发布逻辑，均不计入计时负载。

模拟网关保留真实检索，使用 2 秒/请求固定延迟。当前业务 Agent 在工具返回后还会请求一次规划终止，再请求最终 JSON，所以 RAG 通常是 **3 次模型请求**，通用回答为 1 次；网关不篡改业务执行流程来强行凑成 2 次。这一实际调用数应计入吞吐估算。

## 场景与负载

正常场景以 2.5 秒间隔登录，100 人约需 4 分钟，避免同 IP 30 次/分钟限流。登录不计入问答场景延迟。

| 场景 | 配置 |
|---|---|
| 功能校验 | 1 次真实 HTTP RAG、幂等核对、引用与历史核对 |
| 基线 | 1 人 3 分钟 |
| 读取 | 100 人 10 分钟 |
| 阶梯 | 10、25、50、100 人，每档 5 分钟 |
| 持续 | 100 人混合 30 分钟 |
| 峰值 | 100 人各提一问，模拟重复 3 轮 |
| 故障 | 延迟 8 秒、429、超时 25 秒、worker 重启，各一轮 |
| 持久化 | 重新登录后核对本轮已完成的用户 0 问答原文 |
| 登录峰值 | 同 IP 100 账号并发登录，单独统计预期限流 |

混合选择概率：会话列表 40%、历史 30%、引用 10%、问答 20%；每次完成后停留 10–30 秒。问答中 RAG 70%、通用 30%，每用户至多一个活跃问答。实际完成比例可能因问答耗时变化，报告保留实际请求量。

峰值前建好所有会话，统一屏障放行 100 个任务；客户端记录发送跨度，超过 1 秒或未提交满 100 个，标记 `INVALID_BURST`。不同场景等待队列清空，最多观察 120 秒，并执行 20 次恢复读取。

真实阶段：功能校验计入 10 次预热，随后 100 名用户持续读取，按 10 秒间隔派发 90 个问答，最后 100 问同时提交。网关 SQLite 事务在转发前原子扣减额度；模型失败和重试消耗额度，未被转发的拒绝不消耗。资源监控发现到达 1000 时停止新增负载，存量调用不能越过硬上限。

## 统计、验收与安全停止

记录单调时钟下的计划/实际发送、任务领取、最终结果时间。SSE 记录重连次数，使用 Last-Event-ID；没有 token 流，不报告首 token 延迟。HTTP 202、completed 和有效答案分别计数；RAG 有效要求校验码正确、命中目标片段且所有引用可读，通用回答要求走 general 分支并完成。

| 指标 | 目标 |
|---|---|
| 日常读取 | 成功率 ≥99%，P95 ≤1 秒 |
| 问答提交 | 成功率 ≥99%，P95 ≤1 秒 |
| 混合有效回答 | 成功率 ≥99%，端到端 P95 ≤30 秒 |
| 100 人峰值 | 至少 95 个在 60 秒内有效回答 |
| 引用、会话和持久化 | 无越权、串会话、丢失或错误引用 |
| 峰值恢复 | 2 分钟内无活跃过期任务，读取 P95 ≤1 秒 |

每 2 秒采集 CPU/内存，每约 5 秒采集测试数据库连接、锁等待、任务状态。PostgreSQL 进程资源标注共享集群，包含业务资源竞争。问答排队时间使用测试 worker 的真实领取日志；若任务从未领取，保留空值而不是伪造 0。

发现隔离/数据问题立即停止新增负载；可用内存连续 30 秒低于 10%，或非故障阶段 HTTP 失败比例连续 30 秒超过 20%，停止加压。状态失败但 HTTP 200 的问答仍计入问答失败率，不计入 HTTP 错误率。停止后存量问答有 75 秒客户端观察上限，恢复观察最多 120 秒。故障和登录限流与正常场景分开。

## 结果目录与解读

`runtime/loadtest/latest.json` 指向最新结果目录；每轮独立保留：

- `environment.json`：机器和场景参数；`outcome.json`：停止原因和问答数量。
- `http.jsonl`、`queries.jsonl`、`claims.jsonl`、`gateway.jsonl`、`resources.jsonl`：原始证据。
- `summary.json`、CSV：分场景百分位、成功率、队列和模型调用用量。
- `REPORT.md`、`performance.png`、`resources.png`：结论和曲线。

只执行 smoke 不足以判断 30 分钟稳定性、完整阶梯或真实 DeepSeek 容量；不存在样本的指标用空值，不能作为通过。第一轮若问答失败而读取稳定，结合排队、模型时延、CPU 与数据库锁区分瓶颈，再做优化复测。报告不把模拟结果当作生产 SLA。
