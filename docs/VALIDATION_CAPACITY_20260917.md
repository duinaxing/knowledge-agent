9 月 17 日停止负载后的代表执行计划：会话列表 1.948 毫秒、历史 0.170 毫秒、队列 0.013 毫秒、会话行锁 0.485 毫秒，均使用相关索引。这是事后样本，不能证明峰值期间没有锁或 I/O 等待。

证据指向两个不同问题：多步问答的执行槽位占用导致排队；集中提交还存在连接获取、线程调度和 API 路径开销。下一轮应对 API 同步线程池排队、连接池占用、鉴权重复查询和提交事务做可观测性与单变量对照。不预先增加槽位、延长超时或加入答案缓存；优化后保持同一负载口径复测。
